# 从 RoboTwin 2.0 理解机器人仿真数据合成

## 今日目标

- 阅读 RoboTwin 2.0，理解其双臂机器人仿真数据合成方案。
- 弄清专家程序由谁生成、如何在仿真中自动调试。
- 理解一个 3D 对象要具备哪些操作标注，才能被机器人使用。
- 梳理合成一条完整机器人轨迹需要的信息。
- 区分视觉域随机化和动力学随机化，并理解动力学随机化对 Sim-to-Real 的意义。

## 核心笔记

### 1. 仿真数据合成不是“生成一段视频”

今天最重要的认识是：合成机器人数据的关键不是生成逼真的图片，而是构造一个能够自动变化、自动执行、自动判断结果的闭环任务系统。

RoboTwin 2.0 的基本流程是：

```text
自然语言任务
    ↓
LLM 生成调用技能 API 的专家程序
    ↓
程序在物理仿真中执行
    ↓
执行日志和 VLM 定位错误
    ↓
LLM 修改程序并重新测试
    ↓
获得较稳定的专家程序
    ↓
改变对象、场景、语言和机器人配置
    ↓
反复执行并采集大量轨迹
```

这里必须区分两个阶段：

- **程序生成阶段**：寻找一段能够可靠完成任务的专家逻辑。
- **数据生成阶段**：固定或复用通过验证的专家逻辑，在随机化环境中反复执行，生成大量不同轨迹。

因此，LLM 主要生成的是由抓取、移动、放置、开合夹爪等技能组成的 Python 程序，而不是直接生成每个时间步的关节角。

### 2. 专家程序如何自动调试

在正常流程中，代码主要由 LLM 自主修改，不需要人工逐轮编辑。

每个候选程序在一轮中执行 10 次，系统自动记录：

- 代码是否能够执行；
- 左臂或右臂是否抓取失败；
- 物体是否被放到错误位置；
- 任务最终是否成功；
- 各个执行步骤的相机图像；
- 异常信息和结构化执行日志。

随后，VLM 检查执行图像，尝试判断失败发生在哪一步，以及原因属于代码逻辑、API 使用、抓取还是放置问题。Code Agent 综合结构化日志和 VLM 诊断修改代码，再次运行。

论文设置最多修复 5 轮。当一轮 10 次执行的成功率达到阈值，论文流程图中为大于 50%，程序便可以通过验证。

不过，“自动调试”不等于“完全不需要人工”。整个系统仍依赖人工提前建设：

- 机器人技能 API 和调用示例；
- 任务约束与成功条件；
- 对象的抓取点、功能点和方向标注；
- 机器人模型、控制器和运动规划器；
- 自动流程失败后的人工排查与修复。

论文附录还表明 VLM 诊断并不完全可靠：错误检测准确率约为 43.1%，失败步骤定位准确率约为 30%。因此它更适合作为辅助诊断器，而不应成为唯一的任务裁判。

### 3. 为什么成功判定要依赖仿真真值

VLM 只能根据图像判断“看起来是否成功”，但许多机器人任务的关键状态并不能从有限视角中可靠观察到。

例如在堆叠任务中，VLM 看到两个积木上下排列，可能认为任务成功，但仿真真值可能显示：

- 上方积木只有一个角接触下方积木；
- 积木仍在滑动，即将倒下；
- 姿态偏差已经超过成功阈值；
- 两个积木之间实际上存在细小间隙；
- 积木位于目标区域之外，只是相机视角造成了重合错觉。

仿真器可以直接读取这些不可见或难以判断的信息：

- 物体的真实三维位置和旋转；
- 物体是否位于容器内部；
- 可动关节的实际角度；
- 接触点、接触力和碰撞关系；
- 物体是否仍在运动；
- 夹爪是否真正抓住物体；
- 任务约束是否达到数值阈值。

因此更可靠的做法是：

```text
仿真真值负责最终成功判定
+ 结构化日志负责记录具体错误
+ VLM 负责理解画面和辅助定位原因
```

例如“把杯子放进篮子”的成功条件不应只是“图片里杯子看起来在篮子附近”，而应该明确为：

```text
杯子几何中心位于篮子有效容积内
且杯子与篮子或底面形成稳定接触
且杯子速度低于阈值
且机器人已经松开杯子
```

VLM 适合解释失败现象，仿真真值适合做精确、可重复的验收。二者结合才能减少错误轨迹混入训练集。

### 4. 对象实例、类别与来源

RoboTwin-OD 包含 731 个对象实例、147 个对象类别：

```text
534 个内部重建对象
+ 153 个 Objaverse 对象
+ 44 个 PartNet-Mobility 可动对象
= 731 个对象实例
```

- **类别**表示物体属于哪一种东西，例如杯子、瓶子、鞋、微波炉。
- **实例**表示某个类别下的具体模型，例如黑色马克杯和白色矮杯是两个不同的杯子实例。
- **内部重建对象**由作者通过真实图像或其他方式重建并整理，便于控制模型质量并添加操作标注。
- **Objaverse 对象**来自大型公开 3D 模型库，可增加目标物体和场景干扰物的外观多样性。
- **PartNet-Mobility 对象**带有部件结构和可动关节，例如可以开门的微波炉、可以翻转屏幕的笔记本电脑。

同类多实例可以防止策略只记住一个固定外观。例如训练中出现不同颜色、尺寸和形状的瓶子，模型才更有可能学习“瓶子”及其可抓取区域，而不是只记住某个红色模型。

### 5. 一个可操作对象需要哪些信息

一个漂亮的 3D Mesh 并不等于一个可以被机器人操作的仿真对象。它还需要一份“操作说明书”。

| 信息 | 回答的问题 | 杯子示例 |
| --- | --- | --- |
| 视觉模型 | 相机看到什么？ | 黑色陶瓷表面、杯把和纹理 |
| 碰撞模型 | 哪里会发生物理碰撞？ | 简化后的杯身和杯把轮廓 |
| 放置点 | 物体用哪里接触支撑面？ | 杯底中心 |
| 功能点 | 哪些位置与物体用途有关？ | 杯口、杯把中心 |
| 抓取点 | 夹爪在哪里闭合？ | 杯身中部 |
| 抓取轴 | 夹爪沿什么方向夹紧？ | 从杯身左右两侧夹紧 |
| 对象主轴 | 物体自身的主要朝向是什么？ | 杯底指向杯口的方向 |
| 可行操作方向 | 应怎样接近、施力或移动？ | 从上方放置，沿杯把开口挂入 |

#### 视觉模型与碰撞模型

视觉模型负责外观，包括几何形状、纹理、颜色、材质、粗糙度和反光特性。碰撞模型供物理引擎计算接触，通常比视觉模型简单。

复杂凹形物体经常需要进行凸分解。例如杯子可以被拆成杯身、杯底和若干杯把凸块。碰撞模型不准确时，可能出现夹爪穿模、尚未接触就被阻挡、物体悬浮或接触后被弹飞等问题。

#### 放置点、功能点和抓取点

- **放置点**负责“正确放下”。把杯底中心与桌面目标点对齐，才能避免杯子一半进入桌面。
- **功能点**负责“正确使用”。订书机顶部按压区、杯把中心和微波炉门把手都属于功能点。
- **抓取点**负责“稳定拿住”。锤子的手柄适合抓取，而锤头敲击面更适合作为功能点。

#### 抓取轴、对象主轴和操作方向

- **抓取轴**描述夹爪手指沿什么方向闭合。同一个瓶身抓取点，可以从左右方向夹，也可以将夹爪旋转后从前后方向夹。
- **对象主轴**相当于贴在物体上的局部坐标系。例如鞋跟指向鞋头的方向可作为鞋的前后主轴，用于完成“鞋头朝左”的放置要求。
- **操作方向**描述接近、按压、插入、拉动或旋转的方向。例如按铃要从上向下施力，打开微波炉门要沿铰链允许的方向运动。

这些标注组合后，机器人才能从“场景里有一个杯子”进一步理解为“从杯身侧面抓住杯子，调整杯把方向，再沿挂钩开口把杯子挂上去”。

### 6. 不同机器人需要不同抓取候选

同一个对象和任务，对不同机器人不一定存在相同的最优抓取方法。高自由度机械臂可能适合从上方抓取，低自由度机械臂可能只能从侧面接近。

RoboTwin 2.0 针对对象生成多个候选抓取姿态：

```text
对象标注的抓取方向
  × 多个接近方向
  × 位姿角度扰动
  × 当前机器人的可达性
  × 多次并行运动规划
```

候选姿态还需要通过逆运动学、关节限制、自碰撞和环境碰撞检查。这个过程说明，跨机器人生成数据不能只替换 URDF，还必须重新考虑抓取方式、工作空间和左右臂分工。

### 7. 合成一条完整机器人数据需要什么

一条数据应当是一个完整 episode，而不是单独一张图片或一组关节角：

```text
任务语义
+ 机器人模型
+ 可操作对象及 affordance 标注
+ 场景与物理参数
+ 专家执行程序
+ 运动规划和控制
+ 多模态时间序列观测
+ 连续动作
+ 成功判定
+ 随机化参数与完整元数据
```

每个时间步通常需要记录：

- 一个或多个相机的 RGB、深度或点云；
- 左右机械臂的关节位置、速度和末端位姿；
- 左右夹爪状态；
- 当前时间步执行的动作；
- 必要时保存物体位姿、接触状态等仿真真值。

每条 episode 还应保存任务 ID、语言指令、机器人型号、对象实例、随机种子、随机化参数、帧数、成功标签、失败原因和专家程序版本等元数据。

### 8. 视觉随机化与动力学随机化

RoboTwin 2.0 重点随机化五个方面：

- 桌面干扰物；
- 背景和桌面纹理；
- 光照；
- 桌面高度；
- 语言指令。

这些随机化主要帮助策略适应“看起来不同”的真实环境。可以概括为：

> 视觉随机化让机器人在真实世界中看对；动力学随机化让机器人看对之后还能做对。

真实世界中的质量、摩擦、控制延迟和执行误差不可能与仿真完全一致。如果训练时物理参数始终固定，策略可能学到只在仿真中成立的脆弱动作，甚至利用仿真器的接触漏洞。

实际进行 Sim-to-Real 时，可以进一步随机化：

- 物体质量、重心和惯性；
- 静摩擦与动摩擦；
- 关节阻尼和控制器响应；
- 感知、推理和执行延迟；
- 夹爪摩擦、接触刚度和闭合速度；
- 相机曝光、噪声、模糊与标定误差；
- 深度空洞、边缘噪声和距离误差；
- 关节或末端动作执行误差。

以双臂交接瓶子为例。如果仿真中夹爪永远准时闭合、瓶身摩擦固定且没有控制延迟，策略可能学会右手开始闭合 0.2 秒后左手立即松开。真实机器人中，只要右夹爪慢了几十毫秒，瓶子就会掉落。

经过动力学随机化后，策略更有可能学习：右手闭合后等待、观察瓶子是否稳定、确认抓取成功，再让左手松开。这种根据反馈修正动作的闭环行为，比背诵固定时序更容易迁移到真实机器人。

## 实践与问题

### 问题 1：代码修改是 LLM 自主完成，还是人工完成？

结论：论文设计的是 LLM/VLM 主导的自动调试闭环。正常情况下由 Code Agent 根据执行日志和 VLM 诊断自主修改代码，但系统依然依赖人工建设的技能 API、对象标注、成功条件和仿真基础设施。自动修复彻底失败后，工程上仍可能需要人工介入。

### 问题 2：为什么不能只让 VLM 判断任务成功？

结论：VLM 擅长理解可见现象，但容易受遮挡、视角和细微姿态误差影响。最终成功条件应优先使用物体位姿、关节角度、接触关系和速度等仿真真值，VLM 用于辅助解释和定位错误。

### 问题 3：为什么一个 3D 模型还需要大量操作点标注？

结论：Mesh 只告诉系统物体的形状。抓取点、功能点、放置点和方向标注才能告诉机器人在哪里抓、怎样使用、如何放置，以及应该保持什么姿态。这些 affordance 标注是从“物体建模”走向“机器人操作”的关键桥梁。

### 问题 4：为什么已经做了背景和光照随机化，还需要动力学随机化？

结论：背景和光照变化主要解决视觉差异，不能解决物体更重、表面更滑、夹爪响应更慢等真实物理差异。接触丰富、双臂同步、工具使用、推拉、堆叠和高速动作尤其需要动力学随机化。

### 当前形成的判断

RoboTwin 2.0 最值得借鉴的不是某一种具体模型，而是完整的数据工程思想：

1. 先把对象变成具有操作语义的仿真资产；
2. 用稳定技能 API 限制 LLM 的程序生成空间；
3. 用仿真执行结果和多模态信息自动修复专家程序；
4. 用仿真真值严格过滤轨迹；
5. 在视觉、语言、空间和动力学上扩大训练分布；
6. 保存足够完整的观测、动作、真值和元数据，以便训练与排错。

## 明日计划

- 暂不进行策略训练，先明确 RoboTwin 2.0 或已有策略部署到真实机器人的完整条件。
- 调查支持的机器人本体、机械臂自由度、夹爪型号、相机类型，以及最低计算设备要求。
- 确认部署所需的软件环境，包括操作系统、CUDA、PyTorch、ROS/ROS 2、机器人 SDK、驱动和依赖版本。
- 梳理策略与机器人的控制接口：观测字段、动作表示、控制频率、关节顺序、单位、坐标系和夹爪命令。
- 学习部署前必须完成的标定，包括相机内参、相机外参、手眼标定、双臂基座关系、末端执行器和桌面坐标系。
- 查看真实机器人与仿真环境需要对齐的条件，包括机器人模型、相机视角、工作空间、物体尺寸、控制延迟和动作范围。
- 明确部署安全条件：关节限位、速度与加速度限制、碰撞检测、急停、工作空间保护和人工接管方式。
- 选择一个低风险任务作为部署目标，例如固定场景下抓取瓶子并放入篮子，列出从启动设备到完成一次推理执行的检查清单。
